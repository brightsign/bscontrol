# B-Deploy Setup Template Guide

## Overview

`templates/DefaultSetupPackageTemplateMaster.json` is a Go `text/template` file
that produces a complete B-Deploy setup JSON record. It contains all the fields
the BSN.cloud provisioning API and the on-device `bs-device-setup` process
expect, including firmware definitions for every hardware family, full network
interface configuration, and placeholder tokens for per-deployment values.

The template exists because the `BDeploySetupRecord` Go struct does not cover
every field the API accepts (notably `firmwareUpdatesByFamily` and several
network interface sub-fields). Using the raw template path avoids the lossy
struct round-trip that drops those fields.

## Template Pipeline

```
  DefaultSetupPackageTemplateMaster.json
                  |
     render-setup-template (Go text/template)
       - substitutes CLI/env variables
       - authenticates with BSN.cloud
       - generates a fresh registration token
       - injects token, validFrom, validTo
                  |
           rendered JSON (stdout)
                  |
      bdeploy-add-setup-raw (posts raw JSON)
       - uses AddSetupRecordRaw (no struct marshalling)
       - preserves every field exactly as rendered
                  |
         BSN.cloud provisioning API
```

## Template Variables

These placeholders are replaced at render time. Values come from CLI flags,
falling back to environment variables where noted.

| Placeholder | Source | Env Fallback | Description |
|---|---|---|---|
| `{{.Username}}` | `--username` | `BS_USERNAME` | BSN.cloud user email (bDeploy.username) |
| `{{.NetworkName}}` | `--network` | `BS_NETWORK` | BSN.cloud network name |
| `{{.PackageName}}` | `--package-name` | (none) | Setup package identifier |
| `{{.SetupType}}` | `--setup-type` | `BS_SETUP_TYPE` | `bsn`, `standalone`, or `lfn` (default: `bsn`) |
| `{{.DeviceName}}` | `--device-name` | (none) | Human-readable device name |
| `{{.DeviceDescription}}` | `--device-description` | (none) | Device description text |
| `{{.GroupName}}` | `--group` | `BS_GROUP_NAME` | BSN group name (default: `Default`) |
| `{{.RegistrationToken}}` | (generated) | -- | Token from `GenerateDeviceToken` API |
| `{{.TokenValidFrom}}` | (generated) | -- | Token validity start (ISO 8601) |
| `{{.TokenValidTo}}` | (generated) | -- | Token validity end (ISO 8601) |

`BS_USERNAME` is the BSN.cloud account email (e.g. `user@brightsign.biz`).
This is distinct from `BS_CLIENT_ID`, which is the OAuth client ID used only
for API authentication.

The three token fields are always dynamically generated by calling the
`Provisioning/Setups/Tokens/` API after authentication. They cannot be
overridden from the command line.

## Fields Safe to Change

These fields can be modified in the template without affecting device
provisioning or firmware delivery. They control operational behavior after a
player is set up.

### Deployment Identity

| Field | Default | Notes |
|---|---|---|
| `bDeploy.client` | `"bacon"` | Client identifier; leave as `"bacon"` unless directed otherwise |
| `setupType` | template variable | `bsn` for BSN.cloud managed, `lfn` for local file networking |
| `bsnGroupName` | template variable | BSN group the device joins |
| `deviceName` | template variable | Display name in BSN.cloud |
| `deviceDescription` | template variable | Description text in BSN.cloud |

## Fields That Must Not Be Changed

These fields are structural or are populated by the API/firmware infrastructure.
Changing them will break provisioning or device setup.

### Firmware Definitions (`firmwareUpdatesByFamily`)

The entire `firmwareUpdatesByFamily` section maps hardware families (Impala,
Pantera, Tiger, Pagani, Malibu, Sebring, Raptor, Cobra) to firmware URLs, SHA1
hashes, version numbers, and file lengths. These values come from BrightSign's
firmware release infrastructure. Do not edit them manually. When firmware
versions change, obtain an updated template from BSN.cloud.

### Registration Token (`bsnDeviceRegistrationTokenEntity`)

The `token`, `validFrom`, and `validTo` fields are generated dynamically by the
`GenerateDeviceToken` API. The template placeholders are filled at render time.
Do not hardcode token values.

### Network Interface Identity

| Field | Value | Reason |
|---|---|---|
| `network.interfaces[0].id` | `"wired_eth0"` | Device firmware expects this exact ID |
| `network.interfaces[0].name` | `"eth0"` | Must match physical interface |
| `network.interfaces[0].type` | `"Ethernet"` | Hardware type |

### Required Network Interface Fields

The `bs-device-setup` process expects these fields to be present in each
interface object, even when empty. Missing fields cause setup failures:

| Field | Value | Purpose |
|---|---|---|
| `ip` | `[]` | Static IP addresses (empty for DHCP) |
| `gateway` | `null` | Default gateway (null for DHCP) |
| `dns` | `[]` | DNS servers (empty for DHCP) |
| `metric` | `null` | Route metric |

### Structural Fields

| Field | Value | Reason |
|---|---|---|
| `version` | `"3.0.0"` | API version; must match API endpoint |
| `_id` | `""` | Set by the API on creation |
| `firmwareUpdateType` | `"standard"` | Firmware update strategy |
| `unitNamingMethod` | `"appendUnitIDToUnitName"` | Device naming convention |
| `inheritNetworkProperties` | `false` | Network property inheritance |
| `bsnCloudEnabled` | `true` | Required for BSN.cloud managed setups |

## Tools

### render-setup-template

Renders the template with CLI/env values and a fresh token, outputs JSON to
stdout.

```bash
bin/bsn-render-setup-template \
  --package-name "retail-v1" \
  --network "Production" \
  --username "admin@example.com" \
  --device-name "Lobby Display" \
  templates/DefaultSetupPackageTemplateMaster.json > setup.json
```

### generate-token-json

Generates just the `bsnDeviceRegistrationTokenEntity` JSON object for manual
insertion into a setup file.

```bash
bin/bsn-generate-token-json --network "Production" > token.json
```

Output:
```json
{
  "token": "...",
  "scope": "cert",
  "validFrom": "2026-04-08T15:00:20.000Z",
  "validTo": "2028-04-07T15:00:20.000Z"
}
```

### bdeploy-add-setup-raw

Posts raw JSON to the API, preserving all fields. Accepts a rendered JSON file
or stdin.

```bash
bin/bsn-bdeploy-setup-add-raw setup.json
```

### bdeploy-get-setup

Retrieves a setup record as raw JSON, preserving all fields including
`firmwareUpdatesByFamily`.

```bash
bin/bsn-bdeploy-setup-get --setup-name "retail-v1" --json > retrieved.json
```

## Typical Workflow

```bash
# 1. Render the template with your values
bin/bsn-render-setup-template \
  --package-name "retail-v1" \
  --network "Production" \
  --username "admin@brightsign.biz" \
  templates/DefaultSetupPackageTemplateMaster.json > setup.json

# 2. (Optional) Review the rendered JSON
jq '.bsnDeviceRegistrationTokenEntity' setup.json

# 3. Post to BSN.cloud
bin/bsn-bdeploy-setup-add-raw setup.json

# 4. Verify what was stored
bin/bsn-bdeploy-setup-get --setup-name "retail-v1" --json | jq '.firmwareUpdatesByFamily | keys'
```

## Why Raw JSON Matters

The `BDeploySetupRecord` Go struct covers the most common setup fields but does
not include `firmwareUpdatesByFamily` or several network interface sub-fields
(`ip`, `dns`, `gateway`, `metric`, `showInUi`, `wpaSettings`, etc.). When a
setup record passes through `json.Unmarshal` into the struct and back out via
`json.Marshal`, those fields are silently dropped.

This affects two operations:

1. **Creating setups** -- `AddSetupRecord` (struct-based) drops firmware entries.
   Use `AddSetupRecordRaw` instead.
2. **Reading setups** -- `GetSetupRecord` (struct-based) drops firmware entries
   from the response. Use `GetSetupRecordRaw` instead.

The raw JSON path (`bsn-render-setup-template` -> `bsn-bdeploy-setup-add-raw` ->
`bsn-bdeploy-setup-get`) preserves every field end-to-end.
